# 第一部分 系统规格

## 1 系统全景

### 1.1 一句话

把收购现场的“蓝牙称重、打印箱贴标签”（APP）和后台的“核对、审核、回传好生意入库”（Web + 后端）连成一条线的鸡蛋采购入库系统。

### 1.2 组成

| 部分 | 谁用 | 做什么 |
|---|---|---|
| Android APP | 磅秤员 | 选农户建单、连秤设皮重、逐箱称重自动记录、打印箱贴标签、提交单据 |
| Web 管理端 | 管理员 | 维护基准价、定价规则、规格与皮重、账号、设置；核对、修改、审核单据并回传 |
| 后端 | — | 存数据；全系统唯一算价的地方；对接好生意 |
| 外部依赖 | — | 蓝石蓝牙电子秤、佳博 GP-M32B 标签打印机、畅捷通好生意（ERP） |

### 1.3 一张单从头到尾

```
好生意档案 ──同步──▶ 后端 ◀── Web：基准价、定价规则、设置
                      │
APP：选农户建单 → 连秤设皮重 → 称重自动记录 → 确认计量、打印箱贴标签 → 提交
                      │
                      ▼
    待审核 ──Web 核对，可改──▶ 审核（价格与回传内容定稿）──回传──▶ 好生意采购入库单
```

### 1.4 最大的不确定性

三处外部依赖——秤、打印机、好生意——开发方都无法实测（见 11.1）。这一点决定了本文的三个做法：这三处各用一个接口隔开并配模拟实现（2.2）；它们各有降级路径和可切换的选项（第 4 章）；每个功能如实标注验证到了哪一级（第 11 章）。

## 2 设计原则

这是一个提升农户收货入库效率的小工具，不是高风险系统。每条设计先问一句：**去掉它，收蛋会不会出问题？** 不会，就不做。

### 2.1 四条业务原则

系统的做法都从这四条推出来。每条都写明了“保证到什么程度”，没有保证的也写出来。

**原则一：收蛋不停工。** 外部设备、接口、配置出问题，都不应让现场停下来。
- 秤、打印机、好生意各有降级路径，最后兜底时只要求它们做最少的事（第 4 章）。
- 打印失败不阻断称重与提交，事后可补打。
- 缺定价规则或当日基准价时，默认按 v7 不能提交；可用选项放开，先提交重量、审核前补齐价格。
- 好生意接口不通时，可以先审核、以后再回传，或手工录入后标记为已回传。
- 进行中的单据存在手机本地，APP 被系统回收后重开还在。

**原则二：算钱只有一个口径；已审核的单不随后来的配置变化。**
- 只有后端的计价服务算钱，APP 与 Web 都只展示结果（3.2）。
- 价格在三个时点各记一次，各有用途（3.3）。
- 这不是防篡改：单据没有修改历史；退回待审核后会按当时的配置重新计算。

**原则三：计量可核查。**
- 默认由秤的稳定读数自动记录。
- 凡不是秤直接给出的净重（APP 手工录入、Web 改重），都带“手录”记号，并保留秤最初的读数，供审核人把关（5.2 的约定）。
- 这是给审核人的提示，不是防舞弊机制：管理员本人就能改数。

**原则四：尽量不重复建单。**
- 提交：先取批次号再提交，同一批次号再次提交返回原来那张单（5.2）。
- 审核：同一张单的审核、回传等动作互斥，同时点两次只生效一次（3.4）。
- 回传：好生意明确拒绝时没有重复的风险；没收到答复时可能已经生成，靠提示管理员先核对再重传（3.4）。**这一处没有自动保证。**


### 2.2 只在三处外部边界做接口隔离

| 边界 | 接口 | 真实实现 | 模拟实现 |
|---|---|---|---|
| 好生意 | `ChanjetClient`（后端） | `RealChanjetClient` | `FakeChanjetClient` |
| 蓝牙秤 | `Scale`（APP） | `LanstarScale` | `FakeScale` |
| 标签打印机 | `LabelPrinter`（APP） | `GainschaPrinter` | `FakePrinter` |

这三处恰好也是开发方验证不了的三处。**适配器越薄越好**：凡是能放在适配器之外的逻辑（自动重连、记住上次设备、自动记录、箱数识别、打印队列、备注组装）都放在外面，对着模拟实现验证到 L2；适配器里只剩对厂商 SDK 的直接调用。

其余地方不为“将来可能”写接口，不加 DTO 转换层、用例层、仓储接口这类中间层。一个类只有一个实现时，就直接用这个类。

### 2.3 规则只写一处

| 规则 | 唯一位置 |
|---|---|
| 计价（均重、尾差、价差、单价、金额） | 后端 `PricingService` |
| 均重取整 | 后端 `PricingService`；APP `core` 另有一份只用于称重页实时均重，两边用同一份算例文件保证一致 |
| 秤读数 → 净重、毛重（`Q-03`） | APP `core` 的 `NetWeight.kt` |
| 箱数识别、均摊、零头 | APP `core` |
| 同重归类、回传备注格式 | 后端 `Remark`；APP `core` 另有一份只用于流水页展示，共用算例文件 |
| 单据状态流转 | 后端 `OrderService` |
| 标签排版 | APP `device` 的 `LabelTemplate.kt` |
| 选项的定义与默认值 | 后端 `Options` 注册表；APP 的 `AppOptions` 只镜像默认值 |

Web 不做任何计算，只展示后端返回的结果。

### 2.4 明确不做

对应 v7 第 9 章，写在这里是为了让接手的人不要“顺手加上”：

离线建单与补传 · 重试队列 · 修改历史表 · 缓存 · 消息队列 · 微服务 · 乐观锁（单据操作之间的互斥只靠事务里的一次行锁，见 3.4）· 两个角色以外的权限 · 国际化 · APP 本地数据库 · 依赖注入框架 · Spring Security 全套 · 日志回传 · 定时同步 · 打印记录表 · 设备与手机的后端绑定

### 2.5 自动化测试覆盖范围

- **必须有自动化测试**：计价、取整、箱数识别与均摊、称重状态机、备注组装、单据状态流转、登录失效。这些是算钱和不可逆的地方。
- **不写自动化测试**：页面、弹层、表单、CRUD 接口的逐字段校验。靠对照原型走查和李四算例走通。
- 算例数据只维护一份（`fixtures/`），后端与 APP 的单测都读它。

### 2.6 代码风格

- 命名用英文，界面文案与注释用中文。注释只写“为什么”，不写“做了什么”。
- 不做防御性校验：内部调用之间不重复校验参数；只在接口入口校验用户输入。
- 错误直接抛、统一处理，不层层包装。
- 一个文件超过 400 行时先想是不是混了两件事，而不是先想怎么抽象。

### 2.7 迭代约定

为了改一处不牵连全局：

- **接口只增不改**：可以加字段，不删字段、不改字段含义。APP 忽略不认识的字段，缺的字段用默认值，所以旧版 APP 遇到新后端照常能用。
- **数据库只追加**：每次改表新增一个 Flyway 脚本，不改已发布的脚本。
- **APP 更新不靠应用商店**：部署的站点托管最新的 APK；APP 在登录页和建单页查一次最新版本号，有新版本时给一个下载入口。
- **风险点一处一事**（11.5）：每个适配点只在一个文件里，换掉它不动别处。
- **单据可逆，可人工纠偏**：待审核单可以改、可以作废；已审核未回传的可以退回；回传结果对不上的可以手工标记为已回传。任何一步做错都有办法收拾，不需要进数据库改数据。

## 3 计价、单据与回传

### 3.1 名称对照

v7 的计价公式用字母表示。本文正文与数据库都用业务名称，字母只在这里对照一次。

| v7 公式里的字母 | 含义 | 单位 | 数据库列名 |
|---|---|---|---|
| `W0` | 规格的标准每箱净含量 | kg/箱 | `std_net_kg` |
| `M0` | 当日市场基准价 | 元/箱 | `base_price` |
| `n` | 换算系数：每 1kg 尾差对应的每箱金额差 | 元/kg | 规则表里是 `coef`；冻结到单据上是 `rule_coef` |
| `W` | 批次每箱均重（取整后） | kg/箱 | `avg_kg` |
| `X` | 尾差 = 均重 − 标准净含量 | kg/箱 | 不存，可由上面两项算出 |
| `Y` | 价差 = 换算系数 × 尾差 | 元/箱 | 不存 |
| `M` | 收购价格 = 基准价 + 价差 | 元/箱 | `price` |

### 3.2 计价

后端的 `PricingService` 是全系统唯一算钱的地方。输入：农户、商品、规格、收购日期、各箱净重。

1. 总净重 = 各箱净重之和；原始均重 = 总净重 ÷ 箱数
2. 均重（W）= 原始均重按取整规则取到整数 kg：四舍五入（`.5` 进位）/ 抹零 / 进位
3. 规则 = 该农户绑定的、启用的、商品与规格都相同的收购规则；基准价（M0）= 收购日期当天该规格的基准价
4. 尾差（X）= 均重 − 标准净含量（W0）；价差（Y）= 换算系数（n）× 尾差，四舍五入到分；收购价格（M）= 基准价 + 价差，四舍五入到分；金额 = 箱数 × 收购价格，四舍五入到分

缺规则或缺基准价时不报错，照常返回箱数、总净重、均重，并在 `issues` 里列出 `NO_RULE` / `NO_BASE_PRICE`，单价与金额为空。计价预览接口还接受“换一条规则”或“换一个系数”的试算参数，供 APP 规则弹层预览用（`APP-09`）。

### 3.3 价格的三个时点

单据表里有三组与价格有关的内容，对应三个时点：

| 时点 | 记什么 | 用途 |
|---|---|---|
| APP 提交时 | 当时算出的单价与金额（`submitted_price`、`submitted_amount`） | 审核页对比：现场看到的金额与现在重算的金额不同时标出来 |
| 待审核期间 | 不存。每次打开都按当前的规则、基准价、取整规则实时算 | 补录基准价、修正规则后立即生效，不用重录单据 |
| 审核那一刻 | 冻结计价结果，并存下发给好生意的报文原文（`push_payload`） | 之后再改规则、基准价、税率，这张单的金额和回传内容都不变 |

退回待审核会清空冻结的内容，回到“实时算”。

### 3.4 单据状态流转

```
                  审核                    回传成功 / 标记为已回传
   PENDING ─────────────────▶ APPROVED ─────────────────────────▶ PUSHED
    │  ▲                         │
作废 │  └───── 退回待审核 ────────┘
    ▼
   VOID
```

- 只有 `PENDING` 可以修改表头与流水，也只有 `PENDING` 可以作废。作废的单留在“全部”页签里，批次号不再复用，不能恢复。
- **审核**的前提：有流水、有规则、有基准价。审核动作：冻结计价结果 → 组装报文存入 `push_payload` → 转 `APPROVED`。选项 `push.on-approve = auto`（默认）时紧接着回传一次；`manual` 时到此为止，等管理员点“回传”。
- **回传**：把 `push_payload` 原样发给好生意。成功记 `hs_id` 转 `PUSHED`；失败记 `push_error`，状态仍是 `APPROVED`。首次回传与重新回传是同一个动作。
- `APPROVED` 有三个出口：
  - 回传；
  - 退回待审核（清空冻结字段、`push_payload`、`push_error` 与审核人）。要改任何内容——包括想让新的系统设置生效——都走退回；
  - 标记为已回传：管理员确认好生意里已经有这张单（接口没答复但其实成功了，或是手工录进去的），可填好生意单号，转 `PUSHED`。
- **回传失败分两种，提示不同**：
  - 好生意明确拒绝：`push_error` 记好生意返回的原因。此时好生意侧没有生成单据。
  - 没收到答复（超时、连接中断）：好生意侧可能已经生成了单据。`push_error` 记“没有收到好生意的答复，单据可能已经生成。请先到好生意按单据编号查一下：已经有了，点‘标记为已回传’；没有，重新回传或退回”。不为此另设状态，也不自动去查，由管理员核对。
- **互斥**：审核、回传、退回待审核、标记为已回传、作废、修改这几个动作，各自在一个事务里先锁住这张单据的行（`SELECT … FOR UPDATE`），再检查状态，再动手。修改时表头与流水在同一个事务里整体替换。两个同时到达的审核只有一个会生效；另一个等到锁后发现状态已不是 `PENDING`，直接返回当前状态。
- 事务会跨过对好生意的那次调用，所以这次调用设 15 秒超时。调用途中进程中断的情形不处理：事务回滚后单据停在调用前的状态，再回传会不会重复，取决于好生意是否拒绝重复的单据编号（见 11.5）。

### 3.5 好生意对接

```
ChanjetClient
  listProducts() / listVendors() / listCustomers() / listWarehouses()
  addPurchaseStockIn(payload) → 好生意单据 ID；失败时抛出异常，并区分“好生意明确拒绝”（带原始原因）与“没收到答复”
  bookName()
```

- 字段映射照 v7 7.1；开票类型、税率取审核那一刻的系统设置。`StockInPayload` 是唯一组装报文的地方，只在审核时组装一次（见 3.4）。
- `Remark` 按 v7 5.3 生成备注。选项 `push.remark` 决定带全文、只带汇总还是不带；全文超过 `push.remark-max-length` 时自动降为汇总。
- 配置（环境变量）：`CHANJET_MODE`、`CHANJET_BASE_URL`、`CHANJET_APP_KEY`、`CHANJET_APP_SECRET`、`CHANJET_BOOK_ID`、`CHANJET_OPEN_TOKEN`。`openToken` 的获取与刷新方式以开放平台文档为准，实现在 `RealChanjetClient` 内部，属于适配点。
- `real` 模式下没填密钥：同步与回传都失败并返回清楚的原因，不让服务起不来。

## 4 降级与选项

秤、打印机、好生意的真实表现，开发方和业务方现在都不确定。所以系统要**宽容**：不确定的地方给选项，选错了当场能换；每一处外部依赖都有降级路径，最后兜底时只要求它做最少的事。

### 4.1 降级路径

| 依赖 | 默认（v7 的做法） | 第一级降级 | 最后兜底 |
|---|---|---|---|
| 蓝牙秤 | 秤负责去皮、给稳定标志，APP 自动记录 | APP 自己扣皮、自己判断稳定 | 称重框出现“记录”按钮，按了才记。此时只要求秤能把重量数字传上来。再不行还有手工加一箱（v7 `APP-11`） |
| 标签打印机 | 用 SDK 的文字指令打印 | 整张标签画成图片再发，绕开打印机的字库与编码 | 关闭打印，不影响收蛋与提交 |
| 好生意 | 审核即回传 | 审核与回传分开：先审核，接口通了再点回传 | 在好生意里手工录入后，把单据“标记为已回传” |

### 4.2 什么才做成选项

三条都满足才做，防止选项泛滥：

1. 开发方现在无法验证哪种做法对；
2. 选错了会卡住收蛋、算错钱或回传不了；
3. 两种做法都便宜，而且都能在模拟环境里走到。

其余的不确定只收成一个文件或一个具名常量（见 11.5），不做选项。每个选项的默认值就是 v7 写明的做法，其他取值是降级用的。

### 4.3 选项清单

选项分两组，使用的人不同。默认值写在前面。

**第一组：设备与接口适配。** 联调时由工程师定下来，之后基本不动。

| 选项 | 取值 | 什么时候改 | 生效处 |
|---|---|---|---|
| `scale.tare-by` | `scale`：皮重下发到秤 / `app`：APP 自己扣，不调秤的去皮接口 | 秤的去皮接口不好用，或读数含义搞不清 | APP |
| `scale.reading-is-net` | `true` / `false` | 实测秤的读数未扣皮（`Q-03`）。只在 `scale.tare-by = scale` 时有意义 | APP |
| `scale.stable-by` | `sdk`：用秤给的稳定标志 / `app`：读数在一段时间内几乎不动就算稳定 | 秤的稳定标志不可靠 | APP |
| `scale.stable-window-ms`、`scale.stable-tolerance-kg` | `800`、`0.05` | `scale.stable-by = app` 时记得太早或太晚 | APP |
| `weigh.empty-below-kg` | `5` | “秤面已清空”判断不准 | APP |
| `weigh.merge-tolerance-pct`、`weigh.merge-max-k` | `10`、`8` | 合并称重时“识别不准”的提示太多或太少 | APP |
| `print.render` | `text`：文字指令 / `bitmap`：整张图片 | 标签上文字乱码、缺字 | APP |
| `print.dpi`、`print.offset-x-mm`、`print.offset-y-mm` | `203`、`0`、`0` | 标签内容整体偏大偏小或偏位 | APP |
| `push.remark` | `full`：逐箱 + 归类 / `summary`：只带“共 N 箱”与归类 / `off`：不带备注 | 好生意不接受长备注或备注字段 | 后端 |
| `push.remark-max-length` | `0`（不限） | 实测出备注长度上限（`T-02`）后填入；超过时自动降为 `summary` | 后端 |

**第二组：作业策略。** 随现场情况和管理要求调整。

| 选项 | 取值 | 什么时候改 | 生效处 |
|---|---|---|---|
| `weigh.record-by` | `auto`：稳定后自动记录 / `button`：按“记录”才记 | 自动记录在现场误记或不记 | APP |
| `weigh.merge-detect` | `auto`：按重量识别箱数 / `off`：每次按 1 箱记，箱数在最新一行改 | 箱数识别在现场经常出错 | APP |
| `weigh.manual-entry` | `on` / `off` | 业务方不允许手工录入净重。关掉后秤不可用时无法收蛋 | APP |
| `print.enabled` | `on` / `off` | 打印机暂时用不了，不想让界面一直提示未打印 | APP |
| `submit.without-price` | `block`：缺规则或缺基准价时不能提交 / `allow`：可以先提交，价格在 Web 审核前补齐 | 现场经常因为等规则或基准价而压单 | APP |
| `push.on-approve` | `auto`：审核即回传 / `manual`：审核只锁定，回传另点 | 好生意接口还没调通，但要先把审核做起来 | 后端 |

### 4.4 机制

- 后端有一个选项注册表（`Options` 一个类）：每个选项一行，写明键、所属分组、类型、可选值、默认值、一句“什么时候改”。值存在 `option` 表里，没存过的取默认值。
- 8 项全局业务设置（均重取整方式、标签打印时机、开票类型、税率、标签纸尺寸、标签内容、电子秤型号、打印机型号，见 v7 `WEB-09`）也登记在这个注册表里，单独一组，仍在系统设置页维护。其中与变更 C-1 有关的四项：

  | 键 | 取值（默认在前） | 说明 |
  |---|---|---|
  | `print.timing` | `per-box`：逐箱打印 / `after-confirm`：完成后一次打印 | v7 `APP-07` |
  | `label.content` | `minimal`：净重、批次、批次序号、二维码 / `full`：v7 5.4 的 9 项 | 两种都不印均重 |
  | `device.scale-model` | `lanstar-ble` | 可选值就是实机版里已有适配器的型号；加一个品牌 = 加一个适配器 + 这里加一个可选值 |
  | `device.printer-model` | `gainscha-gp-m32b` | 同上 |
- Web 有一个**高级选项**页（导航“系统”分组下），按注册表自动渲染上面两组：加一个选项不用改 Web。这一页同时显示好生意当前是模拟还是真实，以及模拟模式下的两个失败开关。
- APP 端的选项随 `bootstrap` 接口下发，下一次建单生效。APP 里有同名的 `AppOptions`，带同样的默认值；后端没下发某一项时用默认值。
- 改选项不需要重新打包，也不需要重启。
- 每种取值都要能在模拟环境里走到：模拟台有“读数未扣皮”“稳定标志失灵”“去皮指令无效”三个开关，后端的模拟好生意有“被拒绝”“无答复”两个开关。

**加一个选项只有三步**：注册表加一行 → 在用到它的那一处读它 → 给每种取值补一条测试或走查。

**几条设计说明**

- **一张单 = 一个批次 = 一个商品行**（v7 5.5），所以没有单据明细表。
- **状态只存四种**：待审核、已审核（未回传）、已回传、已作废。“回传中”是一次同步请求进行中的界面状态，不写入数据库。已审核的单，`push_error` 有值就是“回传失败”，没值就是“待回传”。
- **待审核单不存计价结果**：每次读取时按当前的规则、基准价、取整规则实时算。审核那一刻把结果写进“审核时冻结”那组字段，之后改规则不影响它（v7 第 9 章第 7 条）。退回待审核时清空这组字段。
- **回传报文存原文**：审核时把组装好的报文存进 `push_payload`，重新回传就是把它原样再发一次，不重新组装。所以开票类型、税率、档案编码都以审核那一刻为准。退回待审核时清空。
- **单据编号从批次号派生**：批次 `SG20261115-2` 对应单据编号 `CGRK20261115002`，只有一处生成编号。两者生成后不变，之后改收购日期也不变（标签已经打出去了）。
- **档案同步只增改不删**：按 `hs_code` 覆盖更新；好生意里删掉的档案在本系统保留，因为历史单据引用着它。
- **合并称重阈值**是选项 `weigh.merge-tolerance-pct`，默认 `10`，在高级选项页维护，不在系统设置页（v7 `APP-05`）。
- **规则唯一匹配**（农户 + 商品 + 规格只能命中一条启用的收购规则）在 `pricing` 的 Service 里保存时检查，不做数据库约束。

**约定**

- **防重复提交只有一条**：`batch_no` 唯一。两端都是先取批次号再提交，同一次建单的重试复用同一个批次号；同一批次号再次提交，直接返回已有的那张单，客户端当作成功处理。
- **修改是整单覆盖**：`PUT /orders/{id}` 带完整表头和全部流水，后保存的覆盖先保存的。Web 改过净重的箱由前端标上 `manual = true`，并在**第一次**改时把当时的净重记作 `raw_kg`；已经是手录的箱再改，`raw_kg` 保持不变，始终是秤最初的读数（原型已是这个做法，APP 同理）。后端不做逐箱比对。来源为 `WEB` 的自建单不标手录（`WEB-06`）。
- **提交后的标签补打不回写后端**：`printed` 以提交那一刻为准。
- **错误格式**：`{ "code": "...", "message": "给人看的中文" }` 加对应的 HTTP 状态码。只有客户端需要分支处理的情况才定 `code`：

| code | 状态码 | 场景 |
|---|---|---|
| `UNAUTHENTICATED` | 401 | 没登录或登录已失效 |
| `BAD_CREDENTIALS` | 401 | 手机号或密码不对 |
| `WRONG_CLIENT` | 403 | 管理员登 APP，或磅秤员登 Web |
| `RULE_CONFLICT` | 409 | 同一农户在同一商品规格上已有另一条规则；响应里带上冲突的规则与农户 |
| `ORDER_LOCKED` | 409 | 修改一张非待审核的单 |
| `NOT_READY` | 409 | 审核一张缺规则或缺基准价的单 |
| `INVALID` | 400 | 其余输入不合法，`message` 直接显示 |

回传失败不是接口错误：接口正常返回，单据状态为 `APPROVED` 并带 `push_error`。

- **接口快照**：后端启动后由 springdoc 生成 OpenAPI。每次接口有变动，把导出的 `api/openapi.json` 一并提交。Web 的类型由它生成；APP 照它手写接口定义。

### 7.1 分包

按业务分包。包内三层：`Controller` → `Service` → `Mapper`。跨包只调对方的 `Service`，不直接用对方的 `Mapper`。请求与响应用 Java `record`；与表结构一致时直接用实体，不另造一层对象。

### 7.2 登录与权限

- 手机号 + 密码。密码用 BCrypt 存。
- 登录成功返回一个不透明的随机 token，存在 `account.token` 上。账号已有 token 时复用，没有才生成——同一账号在两台设备上登录互不影响。
- 之后每个请求带 `Authorization: Bearer <token>`，拦截器查表得到当前登录人。查不到返回 `401 UNAUTHENTICATED`。
- 重置密码或停用账号时清空 token，该账号在所有设备上立即失效（`BE-05`）。
- 退出登录只清客户端本地保存的 token，不调后端。
- 两个角色：`SCALE`（磅秤员，只能用 APP）、`ADMIN`（管理员，只能用 Web）。登录时带上客户端类型，角色不匹配返回 `403 WRONG_CLIENT`。
- 接口默认只许 `ADMIN` 调用；5.2 接口表里标了“APP”的，`SCALE` 也能调。
- 初始管理员：启动时若没有任何管理员，用环境变量 `EGG_ADMIN_PHONE`、`EGG_ADMIN_PASSWORD`、`EGG_ADMIN_NAME` 建一个。不做管理员管理页面。

### 8.2 做法

- **样式照搬原型**：颜色、缓动变量、类名沿用 `lab/web-sim.html`，把那段 CSS 拆进 `tokens.css`、`base.css` 和各组件。不引入 CSS 框架。

- **Pinia 只放两样**：登录人、导航上的提示数字。页面数据由页面自己请求、自己持有，不做全局缓存。
- **就地编辑统一用 `InlineEdit`**：常驻浅灰虚下划线，点开在值下方的浮层里改（v7 4.5-2）。单据表头、规格与皮重的数值都用它。
- **高级选项页按定义渲染**：`GET /options` 返回每个选项的名称、类型、可选值、默认值、说明和当前值，页面照此画出来，不为单个选项写界面。与默认值不同的项标出来，可一键还原。
- **单据详情的按钮随状态变**：待审核给“审核”和“作废”；已审核未回传给“回传”“退回待审核”“标记为已回传”。列表的“回传失败”页签筛的是全部已审核未回传的单，`push.on-approve = manual` 时页签名显示为“待回传”。
- **新建单先取批次号**：点保存时先 `POST /batches`（带收购日期），再带着它 `POST /orders`。保存失败后重试用同一个批次号，改了收购日期才重新取。
- **`BoxTable` 共用**：单据的逐箱流水抽屉与新建单第 5 步是同一个表格组件。
- **交互约定**照 v7 4.5，逐条在 P5-5 走查。

## 9 Android APP

**技术栈**：Kotlin · 原生 View（XML 布局 + ViewBinding，不用 Compose）· 单 Activity + Fragment · Jetpack Navigation · ViewModel + StateFlow · 协程 · Retrofit + kotlinx.serialization · Material Components（底部弹层）

### 9.1 三个模块

| 模块 | 类型 | 放什么 | 依赖 |
|---|---|---|---|
| `:core` | 纯 Kotlin，不依赖 Android | 重量类型、取整、同重归类、箱数识别与均摊、称重状态机、净重换算、进行中单据模型 | 无 |
| `:device` | Android 库 | `Scale`、`LabelPrinter` 两个接口；`LinkKeeper`；标签数据与模板；Fake 实现；蓝石与佳博适配器 | `:core`、厂商 SDK |
| `:app` | 应用 | 页面、弹层、ViewModel、网络、打印队列、本地草稿 | `:core`、`:device` |

厂商 SDK 只在 `:device` 的两个适配器文件里出现。`:app` 出两种构建包（Gradle 的 product flavor）：模拟版 `sim` 用 Fake 设备并带模拟台，实机版 `real` 用真实适配器；两者只差一个 `DeviceFactory` 和模拟台，其余代码完全相同。

### 9.2 `:core` 里的东西

内部重量一律用整数，单位 0.01kg（与原型一致），只在接口边界与 kg 小数互转。

| 文件 | 内容 |
| --- | --- |
| `Kg.kt` | 重量类型与格式化（去掉末尾的 0；称重框固定 1 位小数） |
| `RoundAvg.kt` | 三种均重取整 |
| `SameWeight.kt` | 同重归类，排序按 5.3 |
| `DetectK.kt` | 按重量识别箱数；识别不准时给两个候选 |
| `SplitBoxes.kt` | 一次称重均摊成 k 条流水，零头入最后一箱；改箱数重新均摊；整组删除；序号顺延 |
| `NetWeight.kt` | 秤读数、每箱皮重、箱数 → 净重与毛重。按 `scale.tare-by` 与 `scale.reading-is-net` 的三种组合换算；读数是否已扣皮（`Q-03`）只在这里处理 |
| `Stability.kt` | `scale.stable-by = app` 时由 APP 判断读数是否稳定 |
| `WeighOptions.kt` | `scale.*`、`weigh.*` 各选项的取值，带默认值 |
| `WeighingMachine.kt` | 称重状态机：未设皮重不记；读数稳定且达到阈值才记（`weigh.record-by = button` 时改为等按钮）；记完须等秤面清空；识别不准时暂停；重称替换指定箱 |
| `Session.kt` | 进行中的单据：建单四项、批次号、皮重、流水、手录与秤原始读数、打印标记；可序列化 |

原型里写死的几个数（净重不足 5kg 视为空秤、识别上限 8 箱、阈值百分比）和几处做法现在都来自 `WeighOptions`。`:app` 从 `bootstrap` 取到后传给 `:core`；`:core` 自己不读配置、不联网。

### 9.3 设备接口契约

界面与状态机只认这两个接口。它们对着 Fake 验证到 L2；联调方的任务就是让真实适配器满足同一份契约。

**`Scale`**

| 成员 | 语义 |
|---|---|
| 连接状态流 | 未连接 / 连接中 / 已连接 / 丢失 |
| 读数流 | 秤回调的重量原值（0.01kg 整数）与是否稳定。**不做扣皮换算**，换算在 `NetWeight.kt` |
| 电量低 | 布尔流 |
| 搜索 | 只返回同类设备：标识、型号、信号强弱 |
| 连接、断开 | 结果体现在连接状态流上 |
| 设数字皮（皮重值）、称重去皮、清皮 | 称重皮与数字皮互斥，切换前的清皮由适配器内部处理。`scale.tare-by = app` 时这三个方法不会被调用 |

**`LabelPrinter`**

| 成员 | 语义 |
|---|---|
| 连接状态流 | 同上 |
| 打印机状态流 | 正常 / 缺纸 / 开盖 / 过热 |
| 搜索、连接、断开 | 同上 |
| 打印一张（已生成好的文字指令，或一张位图） | 挂起直到出结果：成功，或失败及原因 |

**放在适配器之外的逻辑**

| 类 | 位置 | 作用 |
|---|---|---|
| `LinkKeeper` | `:device` | 记住上次连接的设备；登录后自动连；丢失后设备回到附近自动重连。对 `Scale` 与 `LabelPrinter` 通用 |
| `PrintQueue` | `:app` | 逐箱打印（默认，记一箱打一张；重称或手工改过净重的箱立即重打）或完成后依次打印；失败即停，剩下的保持未打印；一键补打；调整过的箱重打。`print.enabled = off` 时整个队列不工作，界面不出现未打印提示 |
| `LabelTemplate` | `:device` | 精简（4 项）与完整（9 项）两套版式的要素位置（mm），由业务设置 `label.content` 选择；两套都没有均重 |
| `DeviceRegistry` | `:app` 的 `real` 源集 | 型号 → 适配器构造函数的一张表（现有 `lanstar-ble`、`gainscha-gp-m32b` 各一行）。实机版按 `bootstrap` 下发的 `device.scale-model`、`device.printer-model` 取适配器，不认识的型号用默认型号；模拟版不看型号，始终用 Fake |
| `LabelRenderer` | `:device` | 按模板生成 TSPL 文字指令，或画成位图；由 `print.render` 选择。位图与模拟台预览是同一段绘制代码 |
| 蓝牙开关与权限 | `:app` | 用安卓系统接口判断，不经过适配器 |

### 9.4 `:app` 的结构

```
app/src/main
├─ MainActivity、AppContainer（手工组装依赖）
├─ data/      Api（Retrofit 接口）、TokenStore、SessionStore（草稿 JSON 文件）、Prefs（上次的仓库、皮重、手机号、服务器地址）
├─ printing/  PrintQueue
├─ ui/
│  ├─ login/ create/ weigh/ summary/ done/      五个页面
│  ├─ sheets/                                    七个底部弹层
│  └─ widgets/                                   步骤卡、称重框、设备卡片、金额
app/src/sim    DeviceFactory（Fake）、模拟台
app/src/real   DeviceFactory（真实适配器）
```

- **一个 Activity 级的 `ReceivingViewModel` 持有整张单的状态**，是整张单在内存里的唯一一份：建单四项、`Session`、`WeighingMachine`、计价预览结果、提交状态。五个页面的 Fragment 只做渲染和转发操作，不各自再设 ViewModel（登录页除外）。
- **本地草稿**：`Session` 每次变化后写入一个 JSON 文件；启动时若有草稿就恢复到称重页。提交成功或放弃整单后删除。这是为了进程被系统回收时不丢已称的箱，不是离线功能。
- **计价只问后端**：汇总页、规则弹层的价格都来自 `POST /orders/quote`。APP 本地只算称重页的实时均重。
- **选项**：`data/` 里的 `AppOptions` 与 第 4 章 的 APP 端选项一一对应并带默认值，从 `bootstrap` 解析，缺项用默认值。
- **新版本入口**：登录页与建单页查一次 `GET /app/version`，比本机版本新就显示下载入口，点了用浏览器下载。
- **登录失效**：任何接口返回 `401` 都转到登录页；重新登录后回到原来的页面，草稿还在。
- **提示音与震动**只用在“记上了”和“出问题了”两种时刻（v7 4.4-3）。

## 10 界面对齐办法

1. 实现一个页面前，在浏览器里打开对应原型，把这一页的每个状态点一遍。
2. 原型下方有数据开关：**演示数据 / 最坏情况 / 最坏 + 100 箱 / 大字号**。实现完成后四档都要过（v7 4.4-6、4.5-6）。Web 另加：1280 宽放大到 130%、宽度小于 1100px。
3. 文案、颜色、间距、动效时长以原型为准；业务规则与原型冲突时以 v7 为准，并记入附录 E。
4. 动效按 v7 4.4-3：称重记录不加动画；其余不超过 250ms；尊重系统“减少动态效果”。

### 11.4 模拟实现是正式交付物

## 14 协作约定

### 14.1 每个任务怎么做

适用于每一个接手任务的人或 agent。

1. **开工前读三样**：本文第 2 章（设计原则）、任务行“引用”列指到的本文章节与 v7 条目、对应的原型函数（附录 B）。
2. **认领**：把看板上自己那一行改成 `进行中`，填负责人与日期。负责人只填角色（开发方 / 联调方）或 `agent`，不填人名、昵称、账号。
3. **一个任务一个分支、一次合入**：分支名 `task/P2-3`，提交信息以任务号开头，如 `[P2-3] 单据修改与 Web 自建单`。
4. **自己先验收**：跑任务行“验收”列写的命令或走查步骤，全过了再把状态改成 `待验收`，填提交号。看板的修改随任务一起提交。
5. **他人验收**：另一个 agent 或人照同一条验收再走一遍，通过后改 `已完成`、合入 `main`。
6. **偏离要留痕**：做的过程中发现本文写得不对、不够或做不到，按自己的判断处理，并在附录 E 追加一行（日期、任务号、变更、原因）；如果推翻了附录 C 里的某条决定，同时把那一行改成新的结论。不悄悄改，也不为此停工等人。
7. **不越界**：只做任务行写明的范围。顺手发现的别处问题记到看板“备注”里，不顺手改。
8. **不暴露个人信息**：提交、PR、文档里不写任何个人信息，详见 14.3。

### 14.2 统一的验收命令

| 范围 | 命令 |
|---|---|
| 后端 | `cd backend && ./mvnw verify` |
| Web | `cd web && npm ci && npm run typecheck && npm run build` |
| APP | `cd android && ./gradlew :core:test :app:assembleSimDebug :app:assembleRealDebug` |
| 全部 | 根目录 `make verify`（依次执行以上三条） |
| 隐私检查 | `scripts/pii-check.sh all`（扫描全部已入库文件）。首次克隆后执行一次 `git config core.hooksPath scripts/hooks`，之后每次提交自动检查 |

涉及界面的任务，除命令外还要按任务行写的步骤走查一遍。Web 走查由 agent 用浏览器完成；APP 的真手机走查由人执行，agent 先在模拟器上自查。

### 14.3 隐私约束

适用于所有人和所有 agent 的全部产出：提交信息、PR 标题与描述、issue、评审意见、文档、代码、注释、看板、测试数据、日志样例。

**不得出现**

- 会话 ID、会话链接（如 `claude.ai/code/session_…`）、agent 的运行 ID 或任务 ID
- 本机路径（如 `/Users/<名字>/…`、`/home/<名字>/…`）。只写仓库内的相对路径
- 与具体的人有关的信息：真实姓名、昵称、用户名、邮箱、手机号、GitHub 或其他平台的账号名、注册信息
- 密钥、token、密码、`.env` 的内容

**可以出现**

- v7 里的示例数据（李四、王秀英、张师傅、王会计及其手机号），它们是虚构的
- `noreply@anthropic.com` 这类署名行
- 厂商、产品与公开文档的名称和地址

**怎么落实**

- 仓库使用中性的提交身份，不要改成个人账号。可接受的只有两种：`egg-dev <egg-dev@users.noreply.invalid>`（人和普通 agent），以及运行环境自带的 `Claude <noreply@anthropic.com>`。git 身份是每个克隆自己的配置，不随仓库走，所以**首次克隆后设置一次**（在本克隆里，不要加 `--global`，否则会改掉个人全局配置）：`git config user.name egg-dev`、`git config user.email egg-dev@users.noreply.invalid`。
- `scripts/pii-check.sh` 在提交时也检查作者和提交者的邮箱，不在这两种身份里就拒绝提交，提示里带着上面两条命令。普通提交在 pre-commit 和 commit-msg 两步都检查；`git merge` 自动生成的合并提交不运行 pre-commit，但会运行 commit-msg，所以合并提交（包括“合并 main”）同样被检查。它只管之后的提交，不改写已有提交；已入库的 `Claude` 身份提交是否统一，由人决定。
- `scripts/pii-check.sh` 在每次提交时扫描暂存区里改动的文件（读的是暂存内容，不是工作区里的同名文件）和提交信息，命中就拒绝提交。通用规则写在脚本里；只属于某个人的词（昵称、邮箱等）各人写在本机的 `.pii-local` 里，一行一个，这个文件不入库。
- 脚本对二进制文件的覆盖有限：docx/xlsx/pptx 会检查文档属性（自定义属性、作者字段、base64 块）和正文，pdf 只检查作者字段；图片等其他二进制文件不扫描，入库前人工确认。Office 文档入库前，另用 `unzip -l` 看一眼有没有 `docProps/custom.xml`（WPS 会在里面存账号与设备信息）。
- 提 PR 前，检查标题和描述里没有上面列出的内容。PR 描述不附会话链接。
- 合并 PR 时自拟合并提交的标题与正文，不用平台默认的 `Merge pull request … from <账号>/…`。标题以 `[Px-y]` 开头，例如 `[P0-1] 合入 main：仓库初始化与隐私检查 (#1)`；正文只写做了什么，不含账号名、分支名里的所有者前缀、会话链接。合并发生在服务端，本地 hook 扫不到，所以靠合并时显式填写。
- 发现已经提交进去的个人信息：删掉并在下一次提交里说明“移除个人信息”，不写被移除的内容是什么。

## 附录 C 当前生效的设计决定

这里只列现在生效的结论和理由。某条决定被推翻时，直接改这里的那一行，并在附录 E 记一笔。

| # | 决定 | 原因 |
|---|---|---|
| 1 | 开发方的交付上限是 L2；三处真实适配器写完但不验证 | 开发方没有秤和打印机，无法调用畅捷通 |
| 2 | 不确定的风险点和作业卡点做成选项，在高级选项页当场切换；三处外部依赖各有降级路径（第 4 章）。不做日志回传 | 现在信息有限，系统要宽容，能在不推翻产品的情况下快速迭代 |
| 3 | 业务设置与高级选项共用一个注册表和一张 `option` 表；高级选项单独成页，不放进系统设置页 | 一套机制，加选项只需注册一行；v7 `WEB-09` 规定识别阈值不在系统设置页，两页面向的人也不同 |
| 4 | 后端与 Web 由联调方自己部署，交 docker compose 一键部署包 | 联调方是工程师，一次性移交 |
| 5 | 单仓库，三端各一个顶层目录；任务与进度看板留在本文里，不拆成单独文档 | 一份规格、一份算例、一张看板管三端 |
| 6 | Web 组件层用 ui-sdk 提供行为，样式照搬原型 | 原型是自定义视觉，这样还原度最高 |
| 7 | 后端持久层用 MyBatis-Plus | 国内 Java 工程师最熟，接手门槛低 |
| 8 | 登录 token 存在账号表上，不用 JWT，不引入 Spring Security | 重置密码与停用要立即失效，查表最直接 |
| 9 | 数据库列名用业务含义，不用公式里的字母（3.1） | 不背公式的人也能读懂字段 |
